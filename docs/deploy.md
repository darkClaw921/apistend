# Развёртывание на проде

Прод — один сервер `apistend.ru` (Ubuntu 26.04, 1 vCPU, 1,9 ГБ RAM, 14 ГБ диска).
На нём же стоит self-hosted раннер GitHub Actions, поэтому деплой не требует
ни SSH-ключей в секретах репозитория, ни доступа снаружи.

## Как едет релиз

```
пуш в main → CI (ubuntu-latest) → зелёный → Deploy (раннер на проде)
```

`Deploy` подписан на `workflow_run` от `CI`, а не на `push`. Иначе деплой уезжал бы
одновременно с тестами и успевал обновить прод раньше, чем те упадут.

Ручной прогон — `workflow_dispatch` в интерфейсе Actions. Ветку он не ограничивает,
но это не имеет значения: развернуть можно только коммит, уже влитый в `main` (ниже).

## Почему в workflow всего один шаг

Джоба состоит из одной строки:

```yaml
run: sudo -n /usr/local/bin/apistend-deploy "$SHA"
```

Ни `checkout`, ни установки зависимостей, ни сборки в ней нет — всё это делает
скрипт на самом сервере, которого нет в репозитории.

Причина в том, что условия `if` в `deploy.yml` защищают **только этот файл**.
Раннер обслуживает весь репозиторий, а метки в Actions сопоставляются как
подмножество: джоба с `runs-on: self-hosted` попадёт на него, метка `apistend-prod`
ничего не ограничивает. В pull request из форка можно принести собственный workflow,
и никакой `if` отсюда его не остановит — единственным барьером остаётся
клик «Approve and run» у мейнтейнера.

Поэтому защита построена так, чтобы попадание чужой джобы на раннер стоило дёшево:

| Кто | Что может |
| --- | --- |
| `runner` | запустить через sudo ровно один скрипт `apistend-deploy`; не читает `/etc/apistend`, не пишет в `/srv/apistend/current`, не состоит в группе `docker` |
| `deploy` | владеет боевым деревом и запускает сервисы; **sudo не имеет вовсе** |

`apistend-deploy` принимает единственный аргумент — полный SHA — проверяет его
регуляркой и разворачивает только если `git merge-base --is-ancestor <sha> origin/main`.
Назвать коммит из чужой ветки или из pull request бесполезно.

Остаточный риск честно назван: чужая джоба всё равно выполняет код на боевой машине
от лица `runner`. Полностью его снимает только вынос раннера с прода — на отдельную
машину, в эфемерный контейнер или на pull-модель.

Настройки репозитория, дополняющие это: `GITHUB_TOKEN` по умолчанию только на чтение,
workflow из форков требуют одобрения для всех внешних контрибьюторов.

## Что делает apistend-deploy

1. `git fetch origin main`, проверка предка, `git checkout --force <sha>`.
2. `pnpm install --frozen-lockfile --prod=false`. Флаг обязателен: при
   `NODE_ENV=production` pnpm выбросил бы `prisma` и `dotenv`, а `dotenv`
   импортируется в рантайме (`apps/api/src/env.ts`).
3. `prisma generate` и `prisma migrate deploy`. Приложение схему само не накатывает.
4. Копия `.next` на жёстких ссылках, останов кабинета, `next build`.
   Сборка упала — возвращается прежняя копия, и кабинет поднимается на ней.
   Мок-шлюз во время сборки продолжает отвечать.
5. Перезапуск обоих сервисов и проверка `/health` и корня кабинета.

API **не собирается**: `tsc -p tsconfig.build.json` падает на `TS5096`, а результат
всё равно нерабочий. Node 26 снимает типы на лету, сервис запускает `node src/server.ts`.
Корневой `pnpm build` тоже не годится — turbo тянет туда сборку api и валит вместе с ней
параллельную сборку кабинета.

## Раскладка сервера

| Что | Где |
| --- | --- |
| Боевое дерево | `/srv/apistend/current`, владелец `deploy`, права 750 |
| Переменные | `/etc/apistend/app.env` (0640, `root:deploy`) |
| Секреты БД и JWT | `/etc/apistend/secrets.env` |
| Сервисы | `apistend-api.service` → 127.0.0.1:8080, `apistend-web.service` → 127.0.0.1:3100 |
| PostgreSQL | контейнер `apistend-postgres`, `/srv/apistend/postgres/`, слушает только петлю; пароль в `.env` рядом, не в `compose.yml` |
| nginx | `/etc/nginx/sites-available/apistend` |
| Раннер | `actions.runner.darkClaw921-apistend.apistend-prod.service`, пользователь `runner`, каталог `/home/runner/actions-runner` |
| Дампы БД | `/var/backups/apistend`, ежедневно в 03:30, семь последних |

## Маршрутизация nginx

Один домен на всё. На API уходят поимённо перечисленные префиксы, остальное —
Next.js:

`/api/` (включая `/api/v1/` — библиотека BX24.js), `/rest/`, `/oauth/`, `/v1/`,
`/b24/`, `/oz/`, `/wb/`, `/custom/`, `/health`.

`/rest/` нужен именно в корне: портал отдаёт приложению голый `DOMAIN`, и приложение
само склеивает `<схема>://<DOMAIN>/rest/<метод>`.

`Upgrade` пробрасывается только в `/v1/` — там единственный WebSocket
(`/v1/tunnel/connect`, туннель `apistend listen`), отсюда же `proxy_read_timeout 3600s`.
`X-Forwarded-Proto` и `X-Forwarded-Host` обязательны: адрес туннеля API строит из
заголовков запроса, и без них CLI получит `ws://` вместо `wss://`.

`X-Forwarded-For` ставится в `$remote_addr`, а не дописывается: Fastify поднят
с `trustProxy: true` и берёт из цепочки крайний левый адрес, так что дописывание
позволило бы клиенту назначить себе любой IP в журнале запросов.

## Память и диск

1,9 ГБ RAM — это и сборка, и PostgreSQL, и оба Node-процесса. Поэтому:

- 4 ГБ swap, `vm.swappiness=10`. Без него OOM-killer убивает `next build`
  с невнятным «Killed».
- `--max-old-space-size`: 1400 на сборку, 768 у API, 384 у кабинета.
- Кабинет останавливается на время сборки.

## Сид на проде не запускается

`pnpm db:seed` создаёт `demo@apistend.ru` с паролем, напечатанным в README публичного
репозитория, и выводит все ключи в stdout — то есть в лог Actions. Учётные записи
на проде заводятся через обычную регистрацию.

## TLS

Сертификат Let's Encrypt на `apistend.ru` и `www`, обновление штатным `certbot.timer`.
По HTTP только редирект на HTTPS; запрос по IP получает 404.

В `/etc/hosts` домен заведён на петлю: лендинг — серверный компонент и делает
`fetch` на `APISTEND_PUBLIC_ORIGIN` изнутри машины.

## Чего эта схема не умеет

- **Откат делается не откатом коммита.** Миграции применяются автоматически и
  необратимы: `revert` в `main` вернёт код, но не схему. Возврат назад — это дамп
  из `/var/backups/apistend` плюс выкатка нужного коммита.
- **Миграция применяется за минуту-другую до перезапуска** — на время сборки кабинета
  новая схема живёт под старым процессом API. Для одного сервера это принято сознательно;
  миграции, ломающие текущий код, нужно разводить на два релиза.
- **Упавшая миграция останавливает конвейер** до ручного вмешательства на сервере.
